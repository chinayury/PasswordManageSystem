# 05 - 开发日志

> 更新日期：2026-11-14
> 适用：密码管理系统 PasswordManageSystem（PDM）

本文档记录缺陷修复（现象→根因→解决方案）、功能新增、架构改进与版本迭代。
完整版本变更见根目录 `CHANGELOG.md`。

## 一、缺陷修复

### BU-11：端口/线程环境变量非法值导致启动崩溃

- **现象**：`run.py` / `wsgi.py` 中 `PORT` / `THREADS` 裸 `int(os.getenv(...))`，
  环境变量手滑写成 `8000t` / `eight` 时启动期直接崩溃，且无任何"哪个配置项错了"的提示。
- **根因**：配置读取缺少容错，非法字符串直接抛 `ValueError` 冒到启动期。
- **解决方案**：统一收口到 `config.serve_port_env()` / `serve_threads_env()`，与
  `_int` / `_float` / `_log_level_env` 同一套"非法值告警 + 回退 + 上下限钳制"机制。

### BU-09：日志级别非法值导致启动崩溃

- **现象**：`.env` 中 `LOG_LEVEL=verbose`（非标准级别名），`create_app()` 抛
  `ValueError: Unknown level`，服务起不来，报错栈指向 logging 模块而非配置项。
- **根因**：`os.getenv("LOG_LEVEL", "INFO").upper()` 后直接交给 `logging.setLevel`，
  无白名单校验。
- **解决方案**：新增 `_log_level_env()`，按合法级别名白名单校验，非法值告警并回退 INFO。

### BU-07：记住我重新认证绕过"改密踢下线"

- **现象**：开启两步验证的用户改密后，其它设备未被强制登出，S-11 踢下线被绕过。
- **根因**：旧实现把"会话里没有纪元"一律当作"首次访问"并静默采纳当前值。但"记住我"
  重新认证路径不携带纪元——设备空闲超过会话 cookie 寿命（12h）而 remember cookie
  仍有效（7 天）时，仅凭 remember cookie 即可重新入座。
- **解决方案**：区分两种"无纪元"情形：①从未在本会话登录过（无 `_user_id`、无
  remember cookie）→正常放行；②由 remember cookie 重新认证而来→强制走一次完整登录，
  让用户在登录表单重新证明身份，而非静默继承新纪元。

### BU-06：僵尸健康审计轮次阻断审计

- **现象**：进程中断后留下的 `running` 状态健康审计行，导致对应 scope 永久无法发起审计。
- **根因**：审计轮次状态机在进程异常退出时未收敛，`running` 行无人接管。
- **解决方案**：启动时 `reap_stale_running_runs()` 将僵尸 `running` 行统一标记为 `failed`。

### BU-15：容器 EXPOSE 端口与 compose 映射不一致

- **现象**：Dockerfile `EXPOSE 8000`，而 compose 映射 `6084:6082`，按 EXPOSE 排查端口
  会踩空。
- **根因**：容器内监听端口与 compose 映射端口未统一。
- **解决方案**：容器内监听端口与 compose 统一为 `6082`，`EXPOSE 6082`。

### B-10：整数/浮点配置非法值导致启动崩溃

- **现象**：`.env` 中 `MAIL_PORT=465#备注`、`HEALTH_MAX_AGE_DAYS=365天` 等手滑写法，
  `ValueError` 冒到 import 期，服务起不来且无提示。
- **根因**：配置读取直接 `int()` / `float()`，无容错。
- **解决方案**：`_int` / `_float` 解析失败时告警并回退默认值，并做上下限钳制。

### B-02：恢复数据库必然失败

- **现象**：Windows 上"恢复数据库"功能必然失败。
- **根因**：`db.init_app()` 从未被调用，请求结束的数据库连接关闭钩子实际未注册，
  连接随应用上下文泄漏，数据库文件长期被占用。
- **解决方案**：在 `create_app()` 中显式调用 `db.init_app(app)`，注册 teardown 关闭钩子。

### Q-01：数据库连接泄漏

- **现象**：同 B-02，数据库连接未在请求结束关闭。
- **根因**：同 B-02。
- **解决方案**：同 B-02。

### S-08：安全拦截器异常时 fail-open

- **现象**：强制改密、会话纪元、空闲锁定等拦截器在自身异常时可能放行，存在安全绕过
  风险。
- **根因**：拦截器 `except` 分支未明确安全策略。
- **解决方案**：统一改为 **fail-closed**——拦截器异常时按"需要拦截"处理（强制改密按
  需改密、纪元/空闲按失效处理），宁可多拦一次，不可放过一次。

### S-11：改密后其它设备未下线

- **现象**：改密/重置后，其它已登录设备仍保持登录态。
- **根因**：缺少会话纪元机制。
- **解决方案**：新增 `users.session_epoch` 字段，改密/重置/注销时递增，会话纪元落后
  即强制登出（详见 BU-07 的记住我修正）。

### S-05：XFF 伪造绕过限流

- **现象**：客户端可伪造 `X-Forwarded-For` 首段轮换"IP"，绕过 IP 维度限流与锁定。
- **根因**：直接采信 XFF 首段。
- **解决方案**：`TRUST_PROXY=true` 时客户端 IP 取 XFF **末段**（由每跳代理追加，末段
  才是代理观察到的真实对端），默认不信任 XFF。

## 二、功能新增（v0.1.0 周期）

- 两步验证（TOTP）：自助开启/关闭、10 个一次性恢复码、半登录状态。
- 密码健康审计：强度评分、重复检测、年龄到期分析、态势评分、HIBP k-匿名泄露查询
  （默认关闭）、Excel 导出（不含密码列）。
- API 密钥：Bearer 密钥、REST API v1、明文查询限流、IP/CIDR 白名单、启停管理。
- 受控共享：按用户共享（只读/可编辑）、过期、撤销。
- 项目分组与重命名。
- 批量导入导出：xlsx/CSV、模板动态生成、公式注入防护。
- 空闲会话自动锁定（`SESSION_IDLE_MINUTES` 可选）。
- 反向代理 XFF 末段解析（`TRUST_PROXY`）。

## 三、架构改进

- **配置容错统一收口**：`_int` / `_float` / `_log_level_env` / `serve_port_env` /
  `serve_threads_env` 形成统一容错体系，所有环境变量读取不再裸转换。
- **启动期维护任务**：过期共享清理、登录锁定清理、预恢复快照清理、僵尸审计轮次收敛、
  数据库结构迁移，统一在 `_register_startup_tasks()` 中执行。
- **安全拦截器集中装配**：强制改密、会话纪元、空闲锁定三个 `before_request` 拦截器
  统一在 `create_app()` 注册，异常一律 fail-closed。
